# CLAUDE.md

Guidance for Claude Code when working in this repo.

## Workflow rules

- **Never `git commit` or `git push` without asking first.** Propose the change, show what would be committed, and wait for explicit approval each time.
- One branch + PR per issue; branch from up-to-date `main`.
- Retry a failed GitHub Pages deploy with a fresh `workflow_dispatch` run — never `gh run rerun` (it duplicates the `github-pages` artifact and the deploy step rejects it).

## Architecture (post repo-split)

- This repo is the **tool only** (extension, MCP server, dashboard source, schema). User data lives in each user's own data repo; the extension's "Set up repo" button installs the data-repo workflow (source of truth: `extension/src/lib/repo-setup.js`).
- Data repos pin the toolchain via `LEETLENS_REF: v1` — a moving major tag. Compatible changes: move `v1`. Breaking changes (schema, index shape, dashboard data contract): new major tag.

## Gotchas

- Monaco models on leetcode.com report LeetCode's own language slugs (`python3`, `golang`, `oraclesql`, `pythondata` for Pandas, …), not Monaco's standard ids.
- The thinking area must be a **block** comment — Monaco doesn't re-insert a line-comment token on Enter, so a `#`-prefixed region turns into live code on the user's second line of notes. `main-world.js` and `leetcode-endpoints.js` each carry their own copy of `THINK_HEADER_RE` (a MAIN-world script can't import); they must stay in sync, and `test/thinking-area.test.mjs` pins the shapes. Never loosen the header pattern to accept `/**` — that would swallow LeetCode's own ListNode template docblock and strip it from the committed solution.
- Run the extension tests with `node --test 'test/*.test.mjs'` — the quotes matter (Node resolves a bare `test/` as a module path).
- The session schema (`data/schema/session.schema.json`) has `additionalProperties: false` — including on `problem`; don't add fields without updating the schema.
- The extension pushes two commits per save (session JSON, then solution file), so data-repo CI must tolerate `main` moving mid-run. **Never resolve that with `git pull --rebase`**: `data/index.json` is generated, so two concurrent runs both regenerate it and the rebase conflicts with itself every time (this is why PR #16's loop failed). Take what landed (`fetch` + `reset --hard origin/main`) and re-run the indexer on top instead.
- The data-repo workflow file is copied into each user's repo at setup time, so `LEETLENS_REF: v1` does **not** ship fixes to it — only to the toolchain under `.leetlens/`. Changing the workflow means every existing data repo must re-run "Set up repo". Keep the workflow thin and put logic in the toolchain where the tag can carry it.
- `data/index.json` in a data repo is generated by its workflow — never edit by hand.
- Writing anything under `.github/workflows/` needs a credential with workflow rights (fine-grained PAT: **Workflows**; OAuth/`gh`: the `workflow` scope). GitHub denies it as a **404**, not a 403 — so a "repo not found" error during repo setup usually means a missing permission, not a missing repo. Plain `gh` cannot push workflow files without `gh auth refresh -s workflow`.
- The Contents API accepts an explicit `branch` on a repo with *no commits* and creates it (making it the default). Empty data repos need no special handling.
- A Contents API PUT **ignores a supplied `sha` when the path doesn't exist and creates the file anyway** (201). So there's no way to "dry-run" a write to probe permissions — don't try; `testConnection` deliberately reports what it cannot verify instead.
